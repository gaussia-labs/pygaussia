# results/ — data behind the notebooks

**The main tour is the notebooks in `jupyter/`, in this order:**

1. **`roastme.ipynb`** — Level 1: the Universal Probe Library, the 3 engines
   (deterministic/rag/graphrag), how they compose, the canonical dataset of 204 probes.
2. **`compare_models.ipynb`** — Level 1b: multi-model GENERATION comparison
   (gemma/GLM/Kimi via HF), the one Alex asked for the paper's table.
3. **`profiler.ipynb`** — Level 2: the real agent evaluated, weakness profile per
   judge, literal inferences, evolution/stability.
4. **`roastme_promptfoo.ipynb`** — generic risk plugins + evasion (inspired by
   promptfoo), multi-turn scaffold. Exploratory, not part of the canonical pipeline.

Plus `demo_roastme_with_outputs.ipynb` / `demo_roastme.ipynb` — a walkthrough of the whole
metric, one with every output saved and one runnable.

They all load **frozen** artifacts from below — no API key is needed
to open them and see the same numbers. If something isn't showing, it needs to be
regenerated by running the corresponding script (see each folder).

## Structure

```
results/
├── level1_probes/              # Level 1 — generated probe dataset
├── level1_probes_generic/      # generic risk plugins (promptfoo, no KB)
├── level1_model_comparison/    # Level 1b — multi-model comparison (Alex)
├── level2_profiler/            # Level 2 — real agent profile (the reported roster)
│   └── archive/                # judges evaluated and then dropped
├── level2_profiler_evasion/    # Level 2 with wrapped query (Base64/ROT13)
├── level2_profiler_multiturn/  # multi-turn scaffold (plumbing, not a real attack)
└── level3_exploiter/           # Level 3 — Exploiter runs (NOT regenerable, see below)
```

The file names within each folder follow a fixed convention generated by
the scripts themselves (`dataset_{kb}_{engine}.json`, `profile_{kb}_{judge}.json`, etc.) —
they're not touched by hand because the scripts and notebooks look them up by that exact name.

### `level1_probes/` — probe generation

- **`dataset_ley_compose.json`** + **`summary_ley_compose.json`** — the canonical
  and current dataset: 204 probes from Ley 24.977, composed of deterministic(65) +
  rag(99) + graphrag(40). This is the one `run_profiler.py` uses by default.
- `dataset_ley_deterministic.json`, `dataset_ley_grag.json`, `dataset_faq_compose.json`
  (+ their `summary_*`) — secondary/exploratory tracks: a single isolated engine, the
  isolated multi-hop GRAG engine, and another KB (FAQ Aurora, not monotributo). Not the
  current Level 2 dataset, kept in case you want to isolate/compare a specific engine.

### `level1_model_comparison/` — multi-model generation comparison

- **`compare_grag.json`** — real run (2026-07-14) of
  `compare_models.py --engine grag` with gemma-4-31B-it/GLM-5.2/Kimi-K2.6 via HF
  (`hf_router`, scale-to-zero). Table + complete probes for each model. It's the
  source of `compare_models.ipynb`.
- `archive/` — old version (2026-07-07) of this same comparison, from before
  Alex requested it formally. Kept for historical reference, not current.

### `level2_profiler/` — real agent profile (target = consultor-monotributo)

- **`transcripts_ley_compose.json`** — the agent's frozen responses to all **204** probes
  (the target was hit once). This is what makes `fixed_transcripts` mode possible: the
  Profiler can be re-run to re-judge these without ever calling the assistant again.
- **`profile_ley_compose_hf-router-<judge>.json`** — the **3 reported judges**: gemma-4-31B,
  GLM-5.2, Qwen3.6-35B-A3B. Each holds `{meta, likely_weaknesses (ω), knowledge_hooks (H),
  graded_probes}` with **151 `graded_probes`** — 204 minus the 53 controls. `meta` carries
  the fail rate (0.1258 / 0.1523 / 0.0795 respectively).
- `profile_ley_compose_groq-llama-3-3-70b-versatile.json` — a fourth judge kept at this level
  for the evasion tracks, which use it.
- **`weakness_evolution_ley_compose.json`** — ranking stability per iteration and judge, plus
  the run config (including `control_probes_excluded`).
- `candidate_judges_test.json`, `candidate_judges_test_round2.json`,
  `glm_logprobs_verification.json`, `qwen3.5-9b_together_logprobs_verification.json`,
  `qwen3.6-35b-a3b_scaleway_logprobs_verification.json` — the evidence for **why this roster**:
  which `model:provider` combos actually expose usable logprobs for a judge-sized prompt.
  Diagnostics, not pipeline inputs.

#### `level2_profiler/archive/` — judges evaluated and dropped

`profile_ley_compose_hf-router-moonshotai-kimi-k2-6.json` and
`profile_ley_compose_groq-llama-3-3-70b-versatile.json`. Kept out of the main directory so
they are not mistaken for the reported roster. Reasoners like Kimi expose no logprobs, so
they fall back to sampling — much slower per call, and the reason the roster changed.

### `level1_probes_generic/` — generic risk plugins (promptfoo, no KB)

No probe is hand-written: a plugin in `config/generic_plugins.yaml` is just a
risk category (name + description); `GenericRiskEngine.generate_proposed()`
(`src/engines_generic.py`) asks the LLM to invent the probes from that description,
optionally anchored to a `--context` describing the agent under test.

- **`dataset_generic.json`** + **`summary_generic.json`** — the canonical dataset: 28
  probes (7 active plugins x 4 each) generated with Gemma, anchored to the
  context of this project's agent (`--context "Assistant for questions about Argentine
  Monotributo..."`). `out_of_scope`, `prompt_extraction`, `system_prompt_override`,
  `excessive_agency`, `hallucination`, `overreliance`, `unverifiable_claims`.
- **`dataset_generic_example_delivery.json`** — secondary example, same code and
  same plugin catalog, but with a `--context` for a food delivery agent
  (not monotributo) — to demonstrate it generalizes to any domain without touching anything.

4 more plugins remain documented as `scaffolded` (`generate_proposed()` skips them) —
see `config/generic_plugins.yaml` for which ones are active vs `scaffolded`.

### `level2_profiler_evasion/` — Level 2 with the wrapped query (Base64/ROT13)

- `transcripts_ley_compose__base64.json`, `transcripts_ley_compose__rot13.json` — 8
  probes each (small sample, groq judge). **Real finding**: 8/8 in both were
  blocked by the response provider's `content_filter` (`claude-opus-4-8`) before
  reaching the assistant's logic — not a harness bug, it's a finding: the
  "decode this and answer" pattern triggers the underlying model's content filter.
  `profile_ley_compose__<evasion>_groq-....json` ends up with 0 graded probes because of this.
  **Folder kept separate on purpose** from `level2_profiler/`: the `profile_{KB}_*.json`
  glob used by `profiler.ipynb` would still match a file with the `__base64` suffix if it
  lived in the same folder.

### `level2_profiler_multiturn/` — multi-turn scaffold

- `transcripts_multiturn_ley_compose.json` — 3 sessions of 2 turns each, same
  `session_id` sustained by `ConversationSession` (`src/target_client.py`). Plumbing
  test (the session persists), **not** a real escalation strategy (not Crescendo)
  — the second turn is a fixed generic follow-up.

### `level3_exploiter/` — Exploiter runs (level 3)

Produced by [`../exploiter/`](../exploiter/), not by anything in `src/`. Twelve
directories, each with four files: `config.json`, `history.jsonl`, `roast_dataset.jsonl`,
`failure_report.json`.

- **`20260729T164442Z-*` (4 dirs) — the runs the paper reports.** `config.json` shows
  `judge_model_name_or_path: google/gemma-4-31B-it:cerebras`, the judge with verified
  logprobs, and `max_steps: 8`.
- `20260721T*` (8 dirs) — earlier runs, kept as the evidence for why the judge was replaced:
  their `config.json` has `judge: None`, i.e. the original self-evaluating `LMJudge`, which
  proved noisy (false positives on an HTTP 500 and on a plain refusal to answer).

Four directories per timestamp are the four `accelerate` ranks of a **single** run, not four
separate runs.

> **These cannot be regenerated.** Each run is stochastic RL (LoRA policy gradient) on 4×T4
> against a live target assistant, so re-running yields different categories. The trained
> adapters from the reported runs no longer exist anywhere. These JSONL files are the only
> record, which is why they are versioned even though `results/` is otherwise scratch.

## Regenerate (optional, needs `.env` with the API keys)

Run from the root of `experiments/` (not from inside `results/` or `src/`):

```bash
PY=.venv/bin/python     # or just `python`, with the venv activated

# level2_profiler/ — the cheap one: re-judges the frozen transcripts, never calls the
# target, needs only HF_TOKEN. The 3-judge roster is already the default.
$PY src/run_profiler.py --dataset results/level1_probes/dataset_ley_compose.json

# level1_probes/ — regenerating this calls an LLM, so the probes will NOT come out
# identical to the committed dataset (generation is stochastic).
$PY src/universal_probe_library.py --kb ley --engine compose
$PY src/generic_probe_library.py --model "google/gemma-4-31B-it" --context "..."   # level1_probes_generic/
$PY src/compare_models.py --engine grag                            # level1_model_comparison/
$PY src/run_profiler.py --dataset results/level1_probes/dataset_ley_compose.json \
   --evasion base64 --judges "groq:llama-3.3-70b-versatile" --iterations 1 --limit 8  # level2_profiler_evasion/
$PY src/run_multiturn_demo.py --limit 5 --turns 2                  # level2_profiler_multiturn/
```

`level3_exploiter/` is not in this list on purpose — see the warning above.
